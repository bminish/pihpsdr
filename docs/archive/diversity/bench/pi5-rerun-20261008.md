# Pi 5 rerun, 2026-10-08: findings

Part of the Pi 5 analysis: [pi5-analysis.md](pi5-analysis.md) (the 2026-10-02 baseline and the plan for this run). Raw output: [pi5-bundle-cm5-20261008/](pi5-bundle-cm5-20261008/).

## Verdict

**No regression, no dropped blocks, no bottleneck.** The Pi 5 still copes with every reference at every rate, with headroom. The worst row on the whole table is RADE V1 on a single-sideband passband at 1536 kHz: 13 % of one core of four.

**One thing was not tested: the functional suite did not run on the Pi.** It stopped at the first build, because the Pi lacks the Opus development headers that `test_props` pulls in through `client_server.h`. That is a gap in the bundle (fixed, below), not a code failure. The suite still passes on the development machine.

## The run

Same module as the baseline: Raspberry Pi Compute Module 5 Lite (Cortex-A76 ×4), `ondemand` 1.5 to 2.4 GHz, Debian trixie, gcc 14.2.0, FFTW 3.3.10, bundle `v3.0-294-g19497e33` (engine as of LC-055). Start 21:20 on 2026-10-08, about 19 minutes. Idle before (load 0.00, 35.6 °C), 35 to 42 °C throughout, no throttling during the run. `throttled=0x50000` was set before the run and did not change, exactly as on 2026-10-02: under-voltage and throttling happened at some point since boot. Still worth checking that module's supply. `perf` was not installed.

The signals are synthetic, only the diversity engine is measured (not WDSP, the GUI or the rest of piHPSDR), and each row was measured once in each pacing.

## Against the baseline

Every row that exists in both runs was compared, worker plus feeder, as a share of one core (36 rows in each pacing). The ratios below are for the rows that cost more than 0.5 % of a core, where a ratio means something.

| | Paced (as the radio runs) | Hot |
|---|---|---|
| Rows over 0.5 % of a core | 28 | 27 |
| Median, new over baseline | ×0.98 | ×1.00 |
| Range | ×0.68 to ×1.28 | ×0.66 to ×1.38 |

The median is 1.0 and the spread goes both ways, so there is no systematic shift.

The first script verdict was NOT CLEAN with four findings. All four are noise, and the script has been corrected:

- **CW 768 kHz paced, +1.09 points (×1.28)** reads **−1.07 points (×0.77) in the hot run.** **CW 384 kHz hot, +0.39 (×1.27)** is −0.14 points paced. Neither reproduces in the other pacing. And **CW Best**, the same engine path, measured in the same run, comes out at 3.90 % at 768 kHz against 3.87 % in the baseline.
- **The two decimator flags (×1.41 and ×1.48)** are on code that did not change at all (`pi_bench`'s own decimators, as in the baseline). So a single paced micro-benchmark on this Pi moves by that much with identical code. `ondemand` clocking is the likely cause; it was not isolated.
- RADE V1 (the correlator was not touched since the baseline except for the copyright line): locked rows ×0.97 to ×1.04 against the baseline, apart from one faster outlier (hot, 192 kHz, ×0.66); searching rows ×0.96 to ×1.10, apart from two faster outliers (hot 192 kHz ×0.71, paced 768 kHz ×0.68). Nothing meaningfully slower.

`compare_pi5.py` now counts a bench_cpu regression only if it shows in **both** pacings (otherwise it prints "noise?"), and a micro-benchmark only if it is over ×1.6. Re-run on these results it says CLEAN. Those tolerances come from this one run; more repeats would pin them down better.

**Engine start, stop and restart** (what the UI thread waits for), wall-clock: first start of the process 3.9 ms; steady start 0.4 to 6.2 ms; restart 0.4 to 6.2 ms, the largest at 1536 kHz (65536 points); stop under 0.04 ms. All far under the 50 ms limit. So switching diversity on, changing the reference, and an Averaging move across 1 s (the 24 to 12 Hz tier, which rebuilds the transform) cannot stall the UI on this Pi.

**The receive thread's per-sample combine** (`rx_add_div_iq_samples`, with the level scale): 4.2 ns a sample on the Pi (2.2 ns on the i7), so 0.02 % of a core at 48 kHz and 0.65 % at 1536 kHz. With the feeder (`diversity_auto_sample`, 1.5 to 1.8 % at 1536 kHz in the baseline) the engine's whole share of the receive thread is about 2.5 % at the highest rate.

**FFT at 65536 points** (ESTIMATE, as the engine plans it): 819 µs a block paced against 969 µs in the baseline.

## What this does not show

- **The GUI side** (the menu's timers, the panadapter's diversity overlay), WDSP, and the rest of piHPSDR are not measured.
- **The functional suite on the Pi.** Not run. Fix below, then `make -C test/diversity run` in the unpacked bundle.
- **Whole-system load.** All figures are the engine alone against synthetic signals, so they are a floor, not a total.
- **How much a single run moves.** Each row once per pacing. The spread seen here (about ±35 % on a row) is why the script now needs both pacings to agree. Three repeats would give a proper noise figure.
- **Real signals.** The scored behaviour (locks, weights) is covered by the suite and the recorded-capture tools, not by this benchmark.

## Follow-ups

- **Bundle:** `libopus-dev` is now in the dependency check (it was missing). On the Pi: `sudo apt install libopus-dev`, then in the existing unpacked `pi5-bench/`: `make -C test/diversity run`.
- **RADE V1 on an AM passband: decided 2026-10-08, no change.** The search follows the passband: one pilot bank when the passband's midpoint is more than 375 Hz either side of the carrier, both only when it straddles it (AM, SAM, FM, DSB). An AM passband with RADE V1 selected would be a real outlier, so the both-banks branch stays as a harmless fallback, the menu is not changed, and the benchmark does not score it.
- **Optimisations** from the 2026-10-02 ranking are still on the shelf and still unnecessary for the Pi to cope: the NEON decimator (3.0× the Pi's decimator; RADE V1 locked at 1536 kHz would go from 13 % to about 7 %), and FFTW wisdom.
